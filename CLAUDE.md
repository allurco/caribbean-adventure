# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Project Caribbean is a turn-based multiplayer naval strategy game (spiritual successor to Merchants & Marauders) for 1 to 4 players: solo against the NPCs, or up to four captains. Built with React + Vite + boardgame.io + React Three Fiber.

## Commands

```bash
npm run dev              # Start dev server (Vite)
npm run build            # Type-check + production build (tsc -b && vite build)
npm run lint             # ESLint (flat config, v9)
npm run preview          # Preview production build
npm test                 # Run all tests once: dots, then failures in full (vitest run --reporter=dot)
npm run test:watch       # Vitest in watch mode
npm run test:db          # Row-level security tests against local Supabase (needs `npx supabase start`, Docker)
npm run test:e2e         # Playwright: two browsers play an online match against the e2e backend (no Docker; ~4 min)
npx tsc --noEmit         # Type-check only (no emit)

npx vitest run src/game/combat.test.ts        # Run a single test file
npx vitest run -t "flee attempt"              # Run tests matching a name
```

Tests use **Vitest** and live next to their source as `*.test.ts`. They run in parallel, one forked process per file on up to 75% of the cores (`vite.config.ts`), and print console output only from failing tests (`silent: "passed-only"`); a test that sends invalid moves on purpose calls `silenceInvalidMoveLogs()` (`src/testSupport/`) to drop boardgame.io's `ERROR: invalid move` log. A long sweep over many seeds is split across files (`villagePlacement.*.test.ts`, `draftPlacement.*.test.ts`, over a shared sweep in `src/testSupport/`, with `seedBlocks.ts` and `sweepCoverage.test.ts` checking that the files cover every seed once) so it does not hold up the run. Game logic is thoroughly unit-tested (~25 suites under `src/game/`); prefer writing tests **before** implementation (TDD). Under `src/board/` the pure modules (the terrain field, meshes, placement, wave and water maths in `visuals/`, grid and camera helpers) are tested the same way; React components and shaders are not, so keep logic out of them.

## Architecture

### Strict Separation: Game State vs. Visuals

**`src/game/`** — All game logic. No rendering, no React, no Three.js. Pure functions plus the boardgame.io `Game` definition. Boardgame.io uses Immer internally, so moves mutate `G` directly.

Logic is split into focused modules; `Game.ts` is the boardgame.io wiring that composes them:
- `Game.ts` — `Game<CaribbeanState>` definition: `setup()`, the two-phase flow, and all `moves` (moves delegate to pure `can*/apply*` helpers in the modules below). Also re-exports `MOVES_PER_TURN` and `getMaxMoves()` (from `turnMoves.ts`), and exports `withSetupData` / `withGeneratedMap` (a game whose `setup()` starts on a pinned size and seed, or on a map already generated) and `withHotseatView` (the game for the seatless hotseat client, which sees the whole table). The seat count is the match's `ctx.numPlayers`, 1 to 4 (`seats.ts`: `MIN_SEATS`, `MAX_SEATS`, `DEFAULT_SEATS = 1`; #278); `setup()` deals one ship and one captain hand per seat, and refuses any other count.
- `playerView.ts` — `playerViewFor(G, playerID)`, the game's boardgame.io `playerView` (#109): what one seat may see. Strips the undealt captain deck, other seats' draft hands, missions and stashed gold, the cargo and gold of rival ships not scouted and NPCs not identified, and, while the draft is on, which captain and ship another seat picked (`draftPicked` marks it picked, #111); no `playerID` is a spectator. boardgame.io's local client applies it too, so tests that read `G` from a seatless client wrap the game in `withHotseatView`.
- `types.ts` — All shared types, including `CaribbeanState` (the root G shape: `cells`, `ships`, `npcs`, `captainDeck`, `draftHands`, `combat?`, `floatingLoot`, …). Re-exported from `Game.ts` for convenience.
- `turnMoves.ts` — The turn's move budget: `getMaxMoves()` (the class's moves less mast damage), `movesLeft()`, `spendMove()` and `turnRunsOut()`, over the per-turn counter `G.movesUsed`.
- `deepSea.ts` — The open sea wears coasters (#340): `isDeepSea(cells, coord, wrap)` (water at least `DEEP_SEA_DISTANCE = 3` hexes from any island or reef, round the seam), `deepSeaHexes` (all of them at once, for the board), `seaWillWear(state, ship)` (a shallow-draft ship with a hull point to spare, on deep sea, no fight on) and `applySeaWear`, run by the main phase's turn `onEnd` for the seat whose turn ends: 1 hull through the usual damage, the last wear of each seat kept in `G.seaWear`. Derived from `G.cells`, never stored. The HUD's warnings (the route hint and End Turn; the board draws no deep-sea tint) and the "open sea strains your hull" line read it through `src/board/seaWearView.ts`.
- `hex.ts` — Pure hex-grid math (cube coords, neighbors, distance, `hexToWorld`).
- `constants.ts` — Ship specs/costs, upgrade definitions, repair costs.
- `mapConfig.ts` / `mapGenerator.ts` — Map size presets + procedural map generation (islands, ports, biomes). `generateWorld` returns the cells and the region table; `generateMap` just the cells.
- `regions.ts` — Regions (#239): five per map, one per nation plus the Pirates (`REGION_NATIONS`, region id = index). Each region's islands are one cluster, its ports fly its flag, channels at least 3 hexes wide (`REGION_CHANNEL`) separate the clusters, and every cell carries `region` (water: its nearest land's). `G.regions` holds each region's nation, seeded name and neighbouring regions.
- `mapRequest.ts` — `resolveMapRequest` (picks the map size and seed: pinned, else random) and `generateMapFor` (runs the generator for that request). Shared by `setup()` and the map worker.
- `moves.ts` — Movement helpers (`validMoveTargets`, `findAccessiblePort`).
- `combat.ts` — Ship-vs-ship combat resolution (seamanship, cannons, boarding, flee, damage/loot): each hit lands at random (#380: `hitLocation`, one die, 1–2 hull, 3–4 masts, 5–6 crew; `rollHitLocations`), and `volleyDamage` deals a volley's hits where they landed (chain shot +1 to the masts and grape shot +1 to the crew when a hit lands there, `shotBonuses`; masts at most `MAX_MAST_DAMAGE`, past which hits go to the hull); `volleyOutcome` gives the shots and the damage too, recorded on each volley as it is fired (`shotBonuses`, `dealt`), so the board reads a volley as it was, never from the shooter's upgrades now; `hitCountsOf` reads a recorded volley, #348's aimed ones included; `resolveFleeAttempt` takes `MAST_FLEE_PENALTY` per point of the fleeing ship's mast damage (up to the cap).
- `combatMoves.ts` — The combat phase's moves as pure helpers over `G` (#345): `atCombatStage` / `canChooseCombatAction` gate each step, and `applyRollSeamanship`, `applyCombatAction`, `applyFleeAttempt`, `applyCannons` and `applyCombatResolution` play it, taking the dice (`d6`) and the turn as arguments and answering `"ended"` when the fight is over (the phase then returns to main). A fight opens with `openFight`: round 1 is the ambush (#346), no draw, the attacker's broadside first; from round 2 a draw decides who acts, each captain rolling its own die (`applyRollSeamanship`, the attacker's, then `applyRollDefenderSeamanship`; against an NPC one press rolls both), a tie to the defender (#347). A ship whose guns cannot reach (`isInGunRange`) never fires first: its draw win offers no fire (an NPC flees instead), and a pursuer out of range fires no parting shot (#356). The cannons fire volley by volley, each one's damage landing before the answer is rolled (`canReturnFire` after it), recorded in order in `G.combat.volleys`. Nobody aims (#380): `applyCannons` fires the first volley (or the parting shot), and a seat's answer is its own step, `returnFire` (`applyReturnFire`), pressed by the side answering; both moves take no argument and refuse an aim sent by an old client (`canFireVolley`; `volleyShooter` names who fires; an NPC's answer fires on its own). Each hit rolls its own location, uniform over hull, masts and crew (`hitLocation`, `rollHitLocations` and `volleyDamage` in `combat.ts`, recorded as each volley's `locations`; `hitCountsOf` reads a volley stored with #348's `aim`): chain shot adds 1 to the masts when a hit lands there, grape shot 1 to the crew when one lands there (`shotBonuses`), and mast damage (a flee penalty too, `MAST_FLEE_PENALTY`) stops at `MAX_MAST_DAMAGE`, 2, past which mast hits go to the hull. The round settles itself in the move that fires its last volley, or the flight caught out of range: `applyCombatResolution` settles the sunk and the derelict and keeps the round in `G.lastRound` (cleared as a new fight opens), which the board and the sounds read for the volleys a step fired (`isVolleyStage`, `volleysFired`, `roundSettledBy`) and the panel shows on the next draw and at the fight's end; the `applyResolution` move stays only for a fight stored at the old `resolution` stage, which either captain may press. The board's turn hand-off waits on the combat director (`fight` phase in `turnHandoff.ts`), so the last volley and a sinking play before the turn passes. Who may press each step stays `combatActor.ts`'s rule, applied by `seatedCombat.ts`. Tests play fights through `src/testSupport/combatSteps.ts`.
- `economy.ts` — Buy/sell goods, upgrades, repair, buying ships, jury-rig.
- `captains.ts` — Captain deck, drafting, home ports.
- `npcManager.ts` / `npcAI` — NPC merchants/flotillas: spawning and movement.
- `eventDeck.ts` — The event deck (#240, #246): `EVENT_DECK_MIX` (the one place the 40-card mix is set; cards whose slice has not landed sit as Calm seas), `shuffleEventDeck` (boardgame.io's `random.Number`), and `drawEvent`, which draws the top card as every main-phase turn ends, reshuffles an empty pile, applies the card (one apply per kind; a card that cannot apply becomes Calm seas) and appends it to the capped public log, all in `G.eventDeck`. Merchants put to sea only through its Merchant convoy card. The turn's end step (`npcTurnStep.ts`, run by the main and combat phases' `onEnd`) sails the flotillas every turn, the merchants once a round (after the last seat's turn), then draws. `playerViewFor` hides the draw pile; the log carries only public facts. The HUD's card and log read the log through `src/board/eventCardView.ts`.
- `reputation.ts` — Bounties, flotilla escalation, pirate status (`isPlayerPirate`, kept per player in `G.pirates`) and the per-flag bounty on pirates.
- `missions.ts` — Mission generation and completion checks (delivery/escort/assassination).
- `scoring.ts` — Gold stashing, combat glory, win condition.
- `scouting.ts` — Scout targeting.
- `ids.ts` — `nextLootId(G)` and `nextMissionId(G, seat)`: loot and mission ids from counters in G (`lootIdCounter`, public; `missionIdCounters`, one per seat, each seat shown only its own by `playerViewFor`; #320), never the clock or module state; `determinismSource.node.test.ts` keeps the clock, `Math.random`, `crypto` and module-level state out of `src/game/`.
- `wind.ts` — The one wind (#204, #264): `windFor(weather)` and the fixed `TRADE_WIND`, a world angle in `hexToWorld`'s frame. Not in `G` yet; rules take it as an argument.
- `weatherGauge.ts` — `holdsGauge(a, b, wind, wrap?)`: which ship is upwind (holds the weather gauge), or null when square to the wind.
- `terrain.ts` — Terrain/elevation logic used by generation.

**`src/board/`** — All rendering. React components that read `BoardProps<CaribbeanState>` and call `moves.*`. No game logic here.
- `Board.tsx` — R3F `<Canvas>` + postprocessing + Tailwind HUD overlay; maps state to the 3D scene and orchestrates all panels/animations.
- `Ship.tsx` — Ship (also `SinkingShip`) sailing as `shipMotion.ts` steps it: one eased curve through the hexes of a move (routed round land by `shipRoute.ts` when it moves several at once), the bow turning at a limited rate, heeling into turns on top of the wave pose. It draws the class's generated model when it has one, else (and while it loads) the hull box from `shipHull.ts`.
- `shipModels.ts` — The ship model catalogue: each `ShipClass` to a model in `public/ships/` (board-variant `.glb` from `boats/`) or none, with its real length and part names; gives the scale (`metresToUnits × SHIP_SCALE`) and the turn from glTF −Z onto the heading. `shipAssetCheck.ts` (with `glb.ts`) holds every file in `public/ships/` to the budget and the catalogue, run by `shipAssets.node.test.ts`; `*.node.test.ts` files use Node's `fs` and are type-checked by `tsconfig.node.json`.
- `HexGrid.tsx` — Hex tile geometry.
- `regionMap.ts` — The regions on the board (#239), pure: border sides between regions, one label position per region (where the event deck's camera flies, #240), label opacity by zoom; drawn by `RegionBorders`, `RegionLabels` and `RegionTooltip`.
- `shaderWarmUp.ts` — The loading gate's shader compile, made as the frames draw (#135): `frameOutputFor(renderOff)`, the one decision whether frames go through the composer or straight to the screen (the board's passes follow it too), and `compileForFrames`, which compiles into a render target for the composer, since three builds each program for the target it draws into. `SceneReadinessProbe.tsx` keeps hidden fading ships and boxes so a sink compiles nothing.
- `seat.ts` — The client's seat (#110): with a `playerID` the board acts only on that seat's turn (`seatMayAct`, `seatMayActInCombat`) and shows that seat's own ship and hand (`ownSeat`, `hudSeat`, `draftView`), never a rival's emptied purse; the glory scoreboard and the "waiting for" lines. Hotseat (no `playerID`) acts and shows for the current player. Dev `?seats=1` puts every seat on one page through boardgame.io's local transport (`loadSeatClient`, `LocalSeats.tsx`).
- `devUrlParams.ts` — also `seatCount(params)`: the local match's seats, solo (1) unless dev `?players=2..4` asks for a hotseat game; `?seats=1` uses the same count (#278).
- `harbour/` — The harbour scene the online shell's still (`public/harbour/`) is captured from (#122); the shell itself shows only the still and never draws it (#418). `HarbourScene.tsx` draws the board's sea, land, decorations and light on one fixed map from one fixed camera, lightened, its waves, surf and palms held through `visuals/motionHold.ts` (the board never holds them) so two captures match (`harbourView.ts` the map and camera, matched to the still; `harbourWorld.ts` the world; `harbourSettle.ts` the settled frame the capture waits on). `HarbourCapture.tsx` is the dev `?view=harbour` the still is captured from (`npm run capture:harbour`, `docs/harbour-still.md`).
- `visuals/` — Environment rendering: the terrain height field (`terrainHeightField.ts`, `sharedTerrainField.ts`), the land mesh (`landMesh.ts`, `useLandTerrain.ts`, `LandTerrain.tsx`), `Ocean.tsx` and its wave/water maths, `TerrainDecorations.tsx` with the placement modules, and the light: `lighting.ts` (`lightingFor(timeOfDay)`, the one source of every lighting value, pinned to `GOLDEN_HOUR` in `sceneLighting.ts`; ADR 0002 amendment b) feeding `SunLight.tsx`, `FillLight.tsx`, the sky map and `PostEffects.tsx`; and the wind: `sceneWind.ts` (`SCENE_WIND`, the game's `windFor(TRADE_WIND)` from `src/game/wind.ts`; `visuals/wind.ts` only re-exports it), read by the wave spectrum, the palms, the reefs' windward foam and the ships' sails and flags (`shipWind.ts`, #204). A source scan over `src/board/` and `src/game/` fails if any other module defines a wind direction. See **Terrain System** below.
- `cardArtSlots.ts` — The event cards' art (#247): one slot per card kind plus the back, each a WebP under `public/cards/` or `null`, as all are until the art lands (a placeholder engraving from `cardPlaceholders.ts` then), held to `public/cards/` by its tests (`cardArtFiles.node.test.ts` the files, through `cardArtCheck.ts`) and on the loading gate through `sceneAssets.ts` (decoded and kept by `cardArtCache.ts`); `cardFlag.ts` tints the Flotilla patrol and Lost flag cards' flags per nation. The dev card lab, `?view=cards`, stages every card.
- Panels & HUD: `EventCard` and `HudEventLog` (the event deck's card and log, over `eventCardView.ts`, #246), `PortPanel`, `MarketPanel`, `ShipyardPanel`, `ShipwrightPanel`, `TavernPanel`, `CombatPanel`, `DraftScreen`, `GameOverScreen`, `Hud*`, tooltips, and animation components.

**`src/audio/`** — Sound, played through three.js audio only: `soundRegistry.ts` (every sound and its CC0 credit; a test keeps it in step with `public/sounds/` and `NOTICE`), `audioEngine.ts` (one `AudioListener` on the camera, unlock on the first user gesture), `audioSettings.ts` (mute and master volume, saved per browser), `soundEvents.ts` / `eventSounds.ts` (game-state changes to sounds, played by `useGameSounds`), and the open-sea ambience bed (`ambienceBed.ts`, with `ambienceMix.ts` crossfading its two layers by camera distance). Keep the logic in the pure modules; `src/board/` only mounts the listener and feeds the bed.

**`src/lab/`** — Dev sandboxes, isolated from game code: the sound lab (`SoundLab.tsx`, at `?view=sound`) to audition every sound and tune the ambience bed, and the shader lab (`ShaderLab.tsx`, at `#lab`).

**`boats/`** — The ship generator, in Python, outside the web app: it drives Blender to build the Frigate, Galleon, Flute and Sloop procedurally (package `boats/frigate/`, one `*Params` per ship) and exports each as a lighter board-variant `.glb` (`export.export_board`, run inside Blender) held to the budget in `board.py`. Its tests are pure and run without Blender: `cd boats && uv run --with pytest pytest tests/ -q`. Only the `.blend` sources under `boats/build/` are tracked; the exported `.glb`s, the baked textures and renders are git-ignored.

**`src/landscape/`** — Phones play in landscape (#123), pure and tested where it can be: `phoneOrientation.ts` (`isPortraitPhone`: a coarse pointer and a device screen whose short side is 540 px or less, so tablets in split view and desktops never; portrait from the window, height ≥ width), `landscapeLock.ts` (full screen then the orientation lock, over the narrow `LockPorts`, feature-checked, never throws), `firstGesture.ts` (the first tap anywhere), `rotateGateLayer.ts` (the gate's z-index, held above every app layer, `*_Z` constant, `index.css` and boardgame.io's debug panel by its test), `rotateGatePresence.ts` (whether the gate is up: window key handlers wrap themselves in `ignoredUnderGate`, and the board's Canvas stops drawing) and `webManifest.node.test.ts` (the manifest in `public/` and `viewport-fit=cover`). `App.tsx` wraps every view in `LandscapeOnPhones`, which makes the view inert and `aria-hidden` under `RotateGate` without unmounting it. Safe-area insets: `src/board/safeArea.ts` holds the rule for each family (`safeInset`, additive, for the HUD; `shellSafeInset`, the larger of margin and inset, for the shell and the gate), and `src/board/useSafeAreaInsets.ts` reads them in pixels for placements worked out in script (the harbour link, ship tooltips, port labels).

**`src/hotseatSave/`** — Saving the local game in the browser (#300), solo or hotseat, pure and tested: `hotseatSave.ts` (`saveHotseat` / `restoreHotseat`: G without the map, which `generateMapFor` rebuilds from size and seed, plus only the cells that differ, ctx, the plugins' data with the dice's PRNG, a fingerprint of the generated world that a restore checks, and a schema version), `parseHotseatSave.ts` (never throws: none, saved, or unreadable by version or corruption), `saveStorage.ts` (one localStorage slot, every call in try/catch, quota errors reported; a finished match clears it; a save that fails to restore is set aside), `autosaver.ts` (debounced writes, flushed on leaving), `hotseatSession.ts`, `describeHotseatSave.ts` (the start screen's summary), `hotseatScreens.ts` (the start screen, voyage and restore-failed transitions; a save is continued only with the seats `?players=` asks for) and `hotseatStoreEnhancer.ts`, the Redux store enhancer passed as the client's `enhancer` option that starts boardgame.io's store in a restored state and reports every state. **Bump `HOTSEAT_SAVE_VERSION` whenever the save's or G's shape changes**; `hotseatSaveShape.test.ts` pins that shape and fails until you do. `src/HotseatGame.tsx` (the start screen, `board/HotseatStartScreen.tsx`, or a voyage) and `src/HotseatVoyage.tsx` (the client, autosaved, inside an error boundary that sets a crashing save aside, and **Save & leave**, `board/HudSaveLeave.tsx`) are thin components. A dev URL that pins the map, or is `?seats=1`, `?snapshot=1` or `?seedGallery=1` (`usesHotseatSave` in `devUrlParams.ts`), never reads or writes the save.

**`src/online/`** — The online shell (#125, the "Harbour launcher" of PRD #104): with a backend the bare root URL opens `OnlineShell`, the sign-in screen then Play, with a nav board (Play, Lobby, Party, Ranked, Profile and the captain's seal), a hanging nameboard and one parchment sheet over `HarbourBackdrop` (#122: the captured harbour still, `HarbourStill.tsx`, and nothing else, #418: no WebGL on the shell's pages; also the app's fallback while the shell's chunk loads; the view and the still's alignment in `src/board/harbour/harbourView.ts`; re-capture the still with `npm run capture:harbour`, `docs/harbour-still.md`), and the party board slot (#119); two layouts, desktop and compact (a phone held sideways, `shellLayout.ts`). It moves between its pages without a reload (`useShellNavigation`, `shellRoute.ts`), so the frame and backdrop stay mounted; Play hosts **Your voyages** (#301: `YourVoyages.tsx` over the pure `voyageList.ts`, read from `GET /api/me/rooms`), and an online match's **Leave to harbour** comes back to it (`harbourPath`, `?saved=1`); Lobby, Party and Ranked show coming sheets; `?skipLogin=1` or the dev URL parameters open the local game. Inside it: the account pages (#105): email magic-link sign-in, and Discord and Google (#106: `ProviderButtons.tsx`; `signInReturn.ts` reads a failed or cancelled return from the URL; the trigger in `supabase/migrations/*_profile_identities.sql` puts the provider's ID, avatar and name on the profile), sign-out, display-name edit (`?view=account`), deleting your account there (#108: `POST /api/me/delete` anonymises the profile to a "deleted player" placeholder, then removes the sign-in; what is personal is listed in one place, `anonymise_profile` in `supabase/migrations/`, every column of `profiles` and every table that references it, which `supabase/tests/profileColumns.test.ts` holds to the migrations; a deleted profile cannot act through `/api`, and its open rooms pass to the lowest seat left) and the public profile (`?view=profile&id=<uuid>`); and online rooms (#112): `?view=rooms` (open a private room), `?view=room&id=<uuid>` (its lobby, polled) and `?view=join&invite=<code>` (the invite link), routed by `onlineRoute.ts`, calling `/api` through `roomApi.ts` (an injected `fetch` and the session's access token); and a started match (#113) at `?view=match&id=<uuid>`, the seat's own board on boardgame.io's `Client` with the `/api` transport (`apiTransport.ts`, a thin class boardgame.io requires, over the pure, tested `matchSync.ts` and `matchApi.ts`), kept live by the match's private realtime channel (#114: `matchChannel.ts`, the topic and the `changed` payload `{ v }` shared with the server; `matchLive.ts`, joining to listen and reconnecting; `useMatchLive.ts`), which falls back to polling whenever it is down; clients send nothing on it, and the seats online come from the server (`server/seatSeen.ts`). Pure, tested modules (`supabaseConfig.ts`, `accountRoute.ts`, `signInReturn.ts`, `avatarUrl.ts` (avatars only from Discord's and Google's image hosts), `shellRoute.ts`, `shellNav.ts`, `shellLayout.ts`, `playActions.ts`, `seal.ts`, `voyageList.ts`, `tabSignIn.ts` (a tab that comes aboard by itself when another tab signs in, #280), `displayName.ts`, `accountService.ts` over the narrow `AccountClient` port in `accountClient.ts`, which tests fake) with thin components on top. `supabaseClient.ts` loads supabase-js lazily, only when `VITE_SUPABASE_*` or the Marketplace's `NEXT_PUBLIC_SUPABASE_*` variables are set; without them the app is the hotseat game, unchanged. Styled with the online shell's tokens (`--font-fell*`, `--font-garamond`, `--color-shell-*`, the `shell-timber-*` and `shell-parchment` texture utilities and the `short-landscape` variant, all in `src/index.css`) and the class strings in `shellStyles.ts`.

**`api/` and `server/`** — The backend's one Vercel Function: `api/index.ts` serves every `/api/*` path (`vercel.json` rewrites them there) through `server/handleApiRequest.ts`, a web-standard `Request → Response` router tested without a server. Add routes there, not files under `api/` (each file there becomes its own function). The function runs **bundled** (ADR 0008): `npm run build` ends with `build:api`, which bundles `server/vercelHandler.ts` with the game code into the git-ignored `api/_server.mjs` that `api/index.ts` loads, because Node's ES modules cannot resolve the game's extensionless imports. The online routes (rooms #112; the move API #113 in `server/matches.ts`, running boardgame.io's reducer through `server/matchEngine.ts` with an allowlist of actions and caps on what a request may cost) take `ApiServices`: the database behind the narrow `OnlineStore` port (`server/onlineStore.ts`; Supabase with the service role in `supabaseOnlineStore.ts`, in memory in tests via `memoryOnlineStore.ts`), the bearer-token check, and the optional `signals` port (`server/matchSignals.ts`: the `changed` signal on the match's realtime channel after an accepted move, over Realtime's REST broadcast with the service role, sent after the response through the optional `defer`, Vercel's `waitUntil` inlined in `server/waitUntil.ts`; left out in tests and the e2e backend); every match read or move also records the seat's `last_seen_at` (throttled) and answers which seats were seen in the last minute (`server/seatSeen.ts`); `servicesFromEnv` builds them from `SUPABASE_URL` and `SUPABASE_SECRET_KEY`, and without them those routes answer 503. The server writes; clients never write rooms, seats or matches, and only ever receive `playerViewFor(G, seat)`. Type-checked by `tsconfig.api.json`.

**`supabase/`** — `config.toml` for the local stack (Supabase CLI, a dev dependency), SQL migrations in `supabase/migrations/` (the schema; `profiles` with row-level security first, then rooms, seats, matches and rate counters, ADR 0008, and the realtime policies of a match's channel, #114) and the database tests in `supabase/tests/`, skipped unless `SUPABASE_DB_TESTS=1` (`branchGrants.test.ts` always runs: each pull request's preview gets its own Supabase branch, #107, which has no default privileges, so a migration must give `service_role` select, insert, update and delete on every table; `20261021000000_service_role_grants.sql` also sets default privileges that cover later tables). A preview handed production's Supabase URL refuses it (`src/online/previewGuard.ts`; on the server through `server/backendStatus.ts`) and shows which database it uses, or that the guard is not configured (`PreviewMarker`). Deployment, env vars, preview branches and local set-up: **`docs/deploy.md`**.

**`src/App.tsx`** — Routes to the labs, the prop viewer (`?view=props`), or the game. The local game, unless a dev URL pins its map or is the seats on one page, goes through `HotseatGame.tsx`: the start screen when a save is stored (Continue voyage or New game, #300), then the voyage (`HotseatVoyage.tsx`), which calls `loadGameClient` with the save to continue, if any. Dev URL parameters (size, seed, camera) are parsed in `src/board/devUrlParams.ts`. For the game, `loadGameClient.ts` generates the map first, in a Web Worker (`src/mapWorker/`, falling back to the main thread when there is no worker or it fails), because boardgame.io's `setup()` is synchronous; it then creates `Client({ game: withHotseatView(withGeneratedMap(Caribbean, map)), board, numPlayers })`, solo by default (`numPlayers: 1`, you against the NPCs; dev `?players=` for more seats, #278). `GameClientLoader.tsx` (`HotseatVoyage.tsx` for the saved game) shows `MapLoadingScreen` until the client is ready. The board mounts its Canvas at once, the captain draft included (`draftScene.ts` leaves out ships with no captain yet), and keeps the loading screen over it (`BoardLoadingVeil.tsx`) until the scene is ready; the draft then opens over the finished scene: every ship model, sound file, web font and the port labels' font loaded, the world built, the sky baked, every shader compiled and a few frames drawn, or a 90 s timeout from page load passed (a file that fails is logged and settled as failed; a ship whose model fails draws its hull box) (`sceneReadiness.ts`, stages and progress, pure; `sceneAssets.ts`, the asset list, held by its test to `public/` and to every loader in `src/`; `useSceneReadiness.ts` and `SceneReadinessProbe.tsx` load and report). A new file the board loads must be registered there. Currently local single-client (no explicit transport). Online play (PRD #104) runs on Vercel Functions and Supabase instead of a boardgame.io server: moves go through `/api`, which runs the same `src/game/` reducer server-side.

### Game Flow (phases)

boardgame.io phases in `Game.ts`:
1. **`draft`** (start phase) — each seat drafts only its own captain from its dealt hand (one pick solo). Every seat still choosing may pick at once (`activePlayers: ALL`, #111), so a seat per client never waits for the seats before it and sees each other seat as picked or still choosing (`draftView` in `seat.ts`); the turns still walk the seats in order, each passing on as its seat picks (`draftOrder.ts`), so the hotseat screen passes the pick from player to player. Once every seat has picked the draft ends on the last seat's turn and `main` begins at seat 0.
2. **`main`** — the core loop. Each ship class sails its own number of moves a turn (`maneuverability`: Sloop 4, Frigate 3, Flute 2, Galleon 1; less one per point of mast damage, at least 1; `getMaxMoves()`). Only sailing a hex (`moveShip`), scouting (`spyglass`) and jury-rigging (`juryRig`) use a move, counted in `G.movesUsed` (reset as each turn begins), not boardgame.io's `ctx.numMoves`; port and ship-management actions (trade, upgrades, repair, buying a ship, stashing gold, the tavern) are free, and an attack ends the turn by starting combat. Ports are safe harbours (#388): no attack or spyglass to or from a ship on a port's docking hex (`safeHarbour.ts`: `atPort`, `harbourKeepsApart`, and `harbourTargets`, which the HUD reads through `src/board/encounterTargets.ts`; only `attackShip` and `attackNPC` call `openFight`, held by `fightOpeners.node.test.ts`). The turn ends by itself when the moves run out, unless the ship is then docked at a port: its captain may still use the port and presses End Turn. `onEnd` sails the NPCs (merchants once a round) and draws an event card (`eventDeck.ts`). `endIf` on the game checks the win condition.

### Coordinate System

Hexagonal grid uses **cube coordinates** `(q, r, s)` where `s = -q - r`, flat-top orientation. `hexToWorld()` in `hex.ts` converts to Three.js world space (XZ plane, Y up). All coordinate math lives in `hex.ts`.

### Terrain System

One terrain height field (ADR 0001) drives everything drawn on or under the sea. `terrainHeightField.ts` builds it from `G.cells` and a seed in pure TypeScript: `sampleHeight(x, z)` in world space, a noise-perturbed coastline, `cell.elevation` setting how high land rises, negative under water; round each port it levels the town's terraces and carves its streets (`townPlateau.ts`, where the port village stands, `villageLayout.ts`). `sharedTerrainField.ts` builds it once per map. `landMesh.ts` samples it into one lattice mesh (land above sea level, seabed below); `terrainFieldTexture.ts` bakes it into a texture the ocean, wave displacement and shore foam shaders read; decorations and the port kit sample it on the CPU. The sea is one surface too (**ADR 0004**, `docs/adr/0004-one-sea-surface.md`): the GPU draws the wave spectrum at the wave clock's time, and `seaSurface.ts` (`createSeaSurface(...).heightAt`) evaluates the same swell band on the CPU for what rides the sea. Full design and the invariants the tests pin are in **`docs/terrain-system.md`** — read it before changing the field or the terrain/ocean shaders.

### Art Direction and Scale

Photorealism is confined to the water and the light; islands, props, ports and ships are our own stylised mid-poly models authored in code (**ADR 0002**, `docs/adr/0002-art-direction.md`). The hex is a board space, not a distance: each family of things carries its own picture factor (**ADR 0006**, `docs/adr/0006-diorama-scale-per-family-factors.md`, which supersedes ADR 0003's ship, building and village scale lines). Ships are ×2.3 on twice true scale (`SHIP_SCALE`, the Frigate's hull 0.44 of a hex, every hull box inside the hex inradius), rocks and stones stay at 115/350 (`PROP_SCALE`), and buildings, landmarks, vegetation and town pieces take `BUILDING_SCALE`, `LANDMARK_SCALE`, `VEGETATION_SCALE` and `TOWN_PIECE_SCALE`, while the water keeps 65 m per world unit (ADR 0003). The factors are named constants in `src/board/visuals/worldScale.ts`, with `PROP_DENSITY`; a new prop takes its family's factor there. Read ADR 0002 and ADR 0006 before adding or reshaping anything visible.

### Seeded World

The same map seed gives exactly the same world on every client; different seeds look different (**ADR 0007**, `docs/adr/0007-seeded-world-variety.md`). Every seeded visual draws from `stream(subSeed(G.mapSeed, "feature", ...ids))` (`src/board/visuals/subSeed.ts`; the feature names live in `seedFeatures.ts`), keyed by the stable ids of `src/board/visuals/islands.ts` (`cellId`, `portId`, `islandId`); nothing visual is stored in `G`. Each island draws an archetype (`islandArchetypes.ts`) and a look within its bands (`islandLook.ts`), which colour, plant and dress it but never change the field. ESLint rejects `Math.random` in game and render code; game randomness goes through boardgame.io's `random`.

### Multiplayer

boardgame.io's rules engine handles all multiplayer; online, its reducer runs in the `/api` function against Supabase (PRD #104), not in a boardgame.io server. All game state changes go through boardgame.io moves — never mutate state outside of moves.

### Styling

All HUD/overlay UI uses **TailwindCSS v4** (via `@tailwindcss/vite` plugin). No CSS modules, no styled-components. 3D visuals use Three.js materials/shaders directly. Postprocessing (bloom, vignette, tone mapping) via `@react-three/postprocessing`.

## Code Conventions

- **Functional TypeScript Only:** No classes. Interfaces/types for data, pure functions for logic.
- **State Serialization:** `CaribbeanState` (G) must stay JSON-serializable at all times — no methods, no class instances.
- **Separation of Concerns:** `src/game/` never imports React or Three.js. `src/board/` holds visuals only and dispatches moves.
- **Relative Imports:** There is **no** path alias configured (no `@/`). Use relative imports (e.g. `import { hexToWorld } from "../game/hex"`).
- **Strict Mode:** TypeScript strict mode, plus `noUnusedLocals`/`noUnusedParameters`. No `any`.
- **Single Responsibility:** Small files, one component per file. New game logic goes in a focused module under `src/game/`, wired into `Game.ts` moves.
